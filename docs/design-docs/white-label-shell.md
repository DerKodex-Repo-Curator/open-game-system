# White-label native shell for OGS games

Status: **decided, building** (grilled with Jon 2026-10-18)
First app: **Rocket Crew**

## Goal

Any OGS game can ship as its own App Store / Play Store app that has the OGS app's native powers
(TV casting, OGS profiles, push links, the app bridge) under the game's own name, icon and store
listing.

## What exists today (checked 2026-10-18)

- `apps/mobile`: one Expo app (`org.opengame.app`, Expo Router, EAS Update with a fingerprint
  runtime). Games run as web pages inside a WebView and talk to the app through
  `@open-game-system/app-bridge-*` (profile, cast, session stores).
- Casting: Google Cast (`_googlecast._tcp`), plus the browser-TV fallback.
- Profiles: OGS game tokens signed by `opengame-api` (JWKS), verified server-side by each game.
- Push links: `opengame.org/join/*` universal links (AASA) and Android App Links.

## Decisions

| # | Question | Decision | Why |
|---|---|---|---|
| 1 | Whose identity does the app show? | **The game's.** OGS is invisible by default, and a game can opt into a "Powered by OGS" mark (`branding: "hidden" \| "powered-by"`). Profiles are still OGS accounts underneath, so one sign-in works across every OGS-powered app and the OGS app. | Jon: "flexible and simple for the dev". The game ships under its own brand, and players don't make an account per app. |
| 2 | Where does the game come from? | **The live web game in a WebView**, with the app bridge. A web deploy updates the app without a store release. | Same model as the OGS app; one codebase for web and native. |
| 2a | What does the TV show when casting? | **The game's own cast screen** in place of the OGS launcher, set through the bridge or shell config. Default: the game's TV page full screen on the OGS receiver, with no launcher chrome. Optional: the developer's own Cast receiver app ID. | Jon wants game-specific cast screens. |
| 3 | Who publishes the apps? | **Each developer**, under their own Apple and Google accounts. They use the OGS native shell for casting and push. | Jon. That makes the shell a developer product (a template plus packages), not a config folder in this monorepo. |
| 4 | Who sends push? | **OGS hosts push.** The developer uploads their APNs key and FCM service account for their bundle ID, and OGS's API sends notifications and push links for that app. | No server for the developer to run. Apple only delivers to an app with a key from that app's own team, so OGS has to hold each developer's key (see the note below). |
| 5 | What does a developer install? | **`create-ogs-app`** (an Expo template) **plus `@open-game-system/shell`** (a package with an Expo config plugin). It needs a great starter and example code. The developer builds with their own EAS account. | Jon. Shell fixes reach developers as package upgrades. |
| 6 | Whose link domain? | **Both.** The developer's own domain is the default (the shell generates AASA and assetlinks). `opengame.org/play/<appId>/…` also routes to the installed app as a fallback for developers without a domain. | Jon: "a, but maybe both". |
| 7 | Customer zero | **Rocket Crew,** published under Jon's Apple team like any other developer. Bundle ID `tv.rocketcrew.app`, name "Rocket Crew", domain `rocketcrew.tv` (ownership to check). It stays available inside the OGS app as well. | Jon: "yes to all". |

| 8 | Sign-in | **Guest first, native upgrade.** The app works at once with a device profile. "Sign in with Apple" (and Google on Android) is a **native** sheet in the shell. The shell trades the identity token with the OGS API for an OGS account, and the game receives the profile and token through the bridge. The web game has no sign-in UI. In a plain browser (the try path) players stay guests. | Native sign-in is what App Review expects, and games don't build auth. |
| 9 | Casting in v1 | **Chromecast only**, plus the existing browser-TV fallback. No AirPlay and no mirroring. | Jon. |
| 10 | Cast screen | The OGS Cast receiver loads the game's manifest `tvUrl` **full screen, with no launcher chrome**. A developer's own receiver app ID is a v2 option. | Jon: ok. `tvUrl` already exists in `ogs-protocol` ManifestSchema. |
| 11 | App Review (4.2) | **Designed for review from day one:** native cast, native push, native sign-in, haptics, a native offline screen, and a template `REVIEW_NOTES.md` in the starter. | Jon: ok. |
| 12 | Money in v1 | **None.** No IAP, no ads. StoreKit bridging is a v2 shell feature. | Jon. |

| 13 | Where a game's app lives | **An `app/` folder in the game's own repo**, generated by `create-ogs-app`. Rocket Crew: `~/src/rocket-crew/app/`. | The game and its app ship together. One repo per game. |

The shell provides the native Cast session and device picker through the app bridge. The shell's own native UI is only the sign-in sheet, the push permission prompt and an offline screen. | It's the same code path a game already uses inside the OGS app. Each game styles its button to match its look. Native code stays small. |
| 15 | Push credential upload | **The `ogs` CLI:** `ogs login`, then `ogs push credentials --ios AuthKey.p8 --key-id … --team-id …` and `--android service-account.json`. **Note on 4.** Today every push goes to one app, `org.opengame.app`, with OGS's own APNs key. A white-label app has a different bundle ID under someone else's Apple team, and Apple only accepts pushes for it signed with that team's key. So "OGS hosts push" means OGS stores a credential per app and picks the right one when sending. The push links and the send API stay the same for games.

## Contract between the pieces (v1)

- **Shell config (`app.config.ts` via the `@open-game-system/shell` plugin):** `appId` (the OGS catalogue id), `gameUrl` (phone page), `name`, `icon`, `splash`, `branding: "hidden" | "powered-by"`, `linkDomains: string[]` (own domain(s); `opengame.org` fallback is always on), `cast: { receiver: "ogs" }`.
- **API additions (`services/api`):**
  - `POST /v1/auth/native` `{ provider: "apple" | "google", identityToken, deviceProfileId? }` → OGS session + profile (links the guest device profile).
  - `PUT /v1/apps/:appId/push-credentials` (ios: p8, keyId, teamId, bundleId; android: service account, package) — encrypted at rest; only the app's owner.
  - Push send picks credentials by the target device's bundle id / package (existing send API unchanged for games).
  - `GET /.well-known/apple-app-site-association` and `assetlinks.json` on opengame.org include every registered app for `/play/<appId>/*`.
- **Cast receiver:** a `chrome: "none"` mode that loads the game's manifest `tvUrl` full screen (no launcher frame) when the sender is a white-label app.
- **CLI (`@open-game-system/cli`, bin `ogs`):** `login`, `push credentials`, `apps register` (bundle id/package ↔ appId), `doctor` (checks AASA, assetlinks, cast receiver, push).

## Build order

1. API + receiver + CLI (independent of any game).
2. `@open-game-system/shell` + `create-ogs-app` template + example code + docs page in `apps/docs`.
3. Rocket Crew: `rocket-crew/app/` from the template, built with EAS under Jon's team (`34S957HD77`), TestFlight internal first.

## Assumptions we haven't written down (ours)

- iOS **and** Android in v1. The shell is Expo, so both come almost free; Play listing is Jon's call later.
- The OGS app keeps working unchanged; the shell is extracted from `apps/mobile`, not a fork (the OGS app becomes the shell's first consumer).
- One game per white-label app (no catalogue of other games inside Rocket Crew's app).
- Rocket Crew's link domain is **open**: `rocketcrew.tv` / `.app` have no DNS (unverified ownership). Until Jon picks one, it uses `opengame.org/play/rocket-crew/…`.
- Developer must enable Push + Sign in with Apple + Associated Domains capabilities on their bundle id (the CLI `doctor` checks what it can).
